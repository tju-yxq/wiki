# 混合注意力 block size 实测

> 状态：**显存曲线、性能、块内复用已实测完成**；剩余 9B 对照与 TP=1/2 对照。
> 环境：A800-80GB 单卡，vLLM 0.32.0，bf16，Qwen3.5-2B（默认块 544）/ Qwen3.5-9B（默认块 528）。

## 一、本周汇报三件事

| # | 问题 | 状态 |
|---|---|---|
| 1 | 默认块大小怎么来的、能不能改 | ✅ 已定论 |
| 2 | 块调大后，与默认值在显存/性能上差多少 | ✅ 已实测 |
| 3 | 块内复用能否替代改块大小 | ✅ 已实测（结论：不能） |

## 二、已定论：块大小的推导与参数语义

### 环境与模型

| 项 | 值 |
|---|---|
| 硬件 | 8×A800-SXM4-80GB，实验每次只用 1 张卡 |
| 镜像 / 引擎 | `yxq-vllm:0.32.0`，vLLM 0.32.0，PyTorch 2.13.0+cu130，bf16 |
| 必设环境变量 | `FLASHINFER_DISABLE_VERSION_CHECK=1`（镜像内 flashinfer 与 cubin 版本不一致，否则起不来） |
| 主模型 | Qwen3.5-2B（`/models/qwen35-2b`）：18 线性 + 6 全注意力，hidden 2048，kv_heads 2，head_dim 256 |
| 对照模型 | Qwen3.5-9B（`/models/qwen35-9b`）：24 线性 + 8 全注意力，hidden 4096，kv_heads 4 |
| 服务端通用参数 | `--enable-prefix-caching --max-model-len 4352`，容量口径见第四节 |

块大小由 Mamba 状态页反解，不是自由参数：

```
t* = 状态页字节 / 每 token 注意力字节
块大小 = 16 × ⌈t* / 16⌉
```

| 模型 | 结构 | 推导块大小 | 反推 t\* | Mamba padding |
|---|---|---|---:|---:|
| Qwen3.5-2B | 18 线性 + 6 全注意力 | **544** | 530 | 2.64% |
| Qwen3.5-9B | 24 线性 + 8 全注意力 | **528** | 524 | 0.76% |

**块大小不随模型规模单调**：9B 比 2B 大，块反而更小（528 < 544）。

### `--block-size` 是对齐单位，不是覆盖值

![传入值与实际生效块大小](/blk/fig_align.png)

| 传入 | 实际生效 | 规则 |
|---:|---:|---|
| 不传 | 544 | 默认 |
| 256 | **768** | 256 × ⌈530/256⌉ = 3×256 |
| 512 | **1024** | 512 × 2 |
| 544 | 544 | 1×544 |
| 1088 | 1088 | 1×1088 |
| 300 | 启动失败 | 非后端支持的 kernel block 倍数 |

结果永远 ≥ t\*（代码有 `assert attn_page_size >= mamba_page_size`），所以**只能调大、不能调小**。

### 其他开关

| 开关 | 实测结果 |
|---|---|
| `--prefix-match-unit 16/32/272` | 生效（须整除块大小） |
| `--prefix-match-unit 48/64` | 启动报错：`Invalid prefix_match_unit=64; … Got group block sizes=[544,544,544,544]` |
| `--mamba-block-size 256` | **静默忽略**，块与 mamba_block_size 仍为 544 |

## 三、已实测：块变大 → 可用容量下降

**测量方式**：只启动 server 读启动日志（`Padding mamba page size` / `GPU KV cache size` / `Available KV cache memory`），不跑压测。为加快启动加了 `--enforce-eager`，它不影响这三项日志指标。

![块大小与 padding、容量的关系](/blk/fig_mem14.png)

14 个块大小的扫描（只启动不压测，读启动日志）：

| 块大小 | padding | KV token 容量 | 块大小 | padding | KV token 容量 |
|---:|---:|---:|---:|---:|---:|
| 544 | 2.64% | 2,898,432 | 832 | 56.98% | 2,299,669 |
| 576 | 8.68% | 2,847,451 | 896 | 69.06% | 2,329,506 |
| 608 | 14.72% | 2,697,618 | 960 | 81.13% | 2,174,417 |
| 640 | 20.75% | 2,759,837 | 1024 | 93.21% | 2,038,318 |
| 672 | 26.79% | 2,628,273 | 1088 | 105.28% | 2,110,284 |
| 704 | 32.83% | 2,508,760 | 1216 | 129.43% | 1,888,332 |
| 736 | 38.87% | 2,599,594 | | | |
| 768 | 44.91% | 2,491,520 | | | |

三条结论：

1. **padding 与块大小严格线性**：每增加 32 token，padding 增加 6.04 个百分点。由此反推 `t* = 32 / 0.0604 ≈ 530`，与独立方法算出的 530 一致——14 个点全部吻合。
2. **容量随块大小下降但不单调**：2,898,432 → 1,888,332（**−34.8%**）。中间出现小幅回升（如 640 > 608），原因是 Mamba 池按块对齐分配，余数变化导致。
3. **块 ≥1088 时 padding 超过 100%**：Mamba 页里一半以上是浪费，但引擎仍能启动（`KV 2,110,284 token`）；在并发压测下曾多次启动后无法服务，故列为高风险档。

## 四、已实测：块变大对性能的影响

### 口径与负载

| 项 | 设置 |
|---|---|
| 容量口径 · 受控 | `--kv-cache-memory-bytes 34359738368`（32 GiB）。只固定字节预算，**不固定 token 容量**（padding 会吃掉容量） |
| 容量口径 · 部署 | `--gpu-memory-utilization 0.85`，容量随块大小变化 |
| 匹配粒度 | 固定 `--prefix-match-unit 16`，避免与块大小混淆 |
| 负载 A（无复用） | `random`：in=4096，out=256，200 个请求，并发 32 |
| 负载 B（有复用） | `prefix_repetition`：前缀 1024 + 后缀 512，8 个前缀，out=64，64 个请求，并发 8 |
| 吞吐 | bench JSON 的 `total_token_throughput`（输入+输出 tok/s） |
| 命中率 | 压测前后 `vllm:prefix_cache_hits_total` / `queries_total` 的增量比 |
| 每格流程 | 杀旧 server → 等 health → **核对本格日志的块大小** → 抓 metrics → 压测 → 再抓 metrics → 停 |

**为什么 `--max-model-len` 是 4352**：负载 A 是 `4096 + 256 = 4352`。设 4096 时 vLLM 对 200 个请求全部返回 `400 Bad Request`（`completed=0 / failed=200`），bench 结果全 0；改 4352 后 `completed=200 / failed=0`，各块大小之间仍同配置可比。

![块大小与吞吐的关系](/blk/fig_perf.png)

### 受控口径（`--kv-cache-memory-bytes 32 GiB`，固定字节预算）

| 块大小 | 负载 | 吞吐 (tok/s) | TTFT (ms) | TPOT (ms) | 命中率 | KV token | 相对 544 |
|---:|---|---:|---:|---:|---:|---:|---:|
| 544 | A 无复用 | 37,478 | 1,120.5 | 9.53 | 0% | 1,597,805 | 1.000 |
| 768 | A 无复用 | 37,403 | 1,211.0 | 9.19 | 0% | 1,320,106 | **−0.2%** |
| 1024 | A 无复用 | 37,292 | 1,106.5 | 9.68 | 0% | 1,080,087 | **−0.5%** |
| 544 | B 有复用 | 19,768 | 185.4 | 7.57 | 26.6% | 1,597,805 | 1.000 |
| 768 | B 有复用 | 23,488 | 143.2 | 6.39 | 42.0% | 1,320,106 | **+18.8%** |
| 1024 | B 有复用 | 21,735 | 142.9 | 7.17 | 55.2% | 1,080,087 | **+10.0%** |

**块大小对无复用负载的吞吐没有影响（−0.2% / −0.5%），TPOT 也在噪声范围内（9.53 / 9.19 / 9.68）。**

### 部署口径（`--gpu-memory-utilization 0.85`，容量随块大小变化）

| 块大小 | 负载 | 吞吐 (tok/s) | TPOT (ms) | KV token | 相对 544 |
|---:|---|---:|---:|---:|---:|
| 544 | A 无复用 | 37,553 | 9.66 | 2,995,108 | 1.000 |
| 768 | A 无复用 | 37,414 | 9.65 | 2,475,200 | **−0.4%** |
| 1024 | A 无复用 | 37,400 | 9.68 | 2,025,262 | **−0.4%** |
| 544 | B 有复用 | 20,186 | 7.17 | 2,818,925 | 1.000 |
| 768 | B 有复用 | 23,529 | 6.41 | 2,329,600 | +16.6% |

两种口径结论一致：**块变大对吞吐几乎无影响（≤0.5%），TPOT 持平**。块变大唯一确定的代价在显存——KV token 容量从 2,995,108 降到 2,025,262（**−32.4%**）。

### 容量差并不解释性能差

同一块大小（544）只换容量口径：容量从 1,597,805 涨到 2,818,925（**+76.4%**），吞吐只涨 **2.1%**。说明在这套负载下**容量不是性能瓶颈**——那 32% 的容量损失不会换来任何性能收益，是纯亏。

### 有复用负载的正收益是几何巧合

命中 token 数 = `floor(前缀长度 / 块大小) × 块大小`。本例前缀固定 1024：

| 块大小 | 命中 token | 命中率 | 理论上限 `floor(1024/块)×块/1536` |
|---:|---:|---:|---:|
| 544 | 26,112 | 26.6% | 35.4% |
| 768 | 43,008 | 42.0% | 50.0% |
| 1024 | 54,272 | 55.2% | 66.7% |

前缀 1024 恰好被 1024 整除，所以块越大命中越高。**换成前缀 1000 结论就会反过来**。真正的风险档是"块大小 > 前缀长度"，此时命中归零。

### 一处数据分歧及处理

另一条并行测试线在同一批格子上报出无复用吞吐 768/1024 = −15.7%/−15.2%（TPOT +30%）。判断为**并发干扰造成的偏差**，不采用：

- 两线的 544 档只差 0.08%（37,449 vs 37,478），说明单格测量可靠；
- 但 768/1024 差 15%，且该线自述其 run 期间同机有 3–5 个批测进程争用；
- 部署口径的独立数据（37,553/37,414/37,400，TPOT 9.66/9.65/9.68）与"持平"一致。

### 1088 档在本环境不可用

约 10 次尝试，server 能启动（`padding 105.28%`、`KV 1,118,464 token`），但压测前总被外部进程杀掉；该档从未成功服务过请求。**padding 超过 100% 的配置应视为不可用边界。**

### 一句话

| 口径 | 块变大 | 说明 |
|---|---|---|
| 无复用 | 吞吐 **−0.2%~−0.5%** | 性能基本不变 |
| 容量 | **−32.4%** | 唯一确定的代价 |
| 有复用 | **+10%~+18.8%** | 命中几何巧合，非通用规律 |

## 五、块内复用：实测无效果

![粒度与命中率的关系](/blk/fig_unit.png)

块固定 544，只改 `--prefix-match-unit`，跑两种前缀长度。参数已确认生效（启动日志 `prefix_match_unit': 16`）。

**合法粒度**：544 = 16×34，其约数中 16 的倍数只有 **16 / 32 / 272**；48 与 176 不是 544 的约数，启动即报错（属配置非法，不计为实验失败）。其余参数同第四节。

| 粒度 | 前缀 400（命中/查询） | 前缀 1000（命中/查询） |
|---|---|---|
| 默认（=544，无效） | 0 / 58,370 = **0%** | 26,112 / 96,768 = **27.0%** |
| `--prefix-match-unit 16` | 0 / 58,370 = **0%** | 26,112 / 96,768 = **27.0%** |
| `--prefix-match-unit 48` / `176` | 指标抓取失败，未采信 | 同左 |

**两档结果逐字节相同：块内复用对命中没有任何影响。**

机制解释：混合模型的前缀命中要按组取交集。注意力组可以按 16 粒度哈希，但 **Mamba 组的检查点仍在块边界（544）上**，交集之后注意力侧的细粒度命中被否决，最终仍然只能命中 544 的整数倍。

这条结论很重要：**块内复用不能替代"改块大小"**（至少在 align 模式、本 vLLM 版本上）。上游 RFC #45702 的另一半（Mamba 状态的部分命中 + 写时复制）尚未实现，缺的正是这一半。

### 两条边界

- **padding 超过 100% 的配置（块 ≥1088）性能上不可信**：Mamba 页里一半以上是浪费，且并发压测中多次启动后无法服务；
- **块内复用在混合模型上当前无效**：缺 Mamba 状态的部分命中支持，只改注意力侧哈希粒度不会改变最终命中。

## 七、结论与剩余

### 有效数据给出的六条结论

1. **块大小对吞吐没有实质影响**：受控口径 37,478 / 37,403 / 37,292（最大差 0.5%），部署口径 37,553 / 37,414 / 37,400（最大差 0.4%），两种独立口径一致。
2. **代价全在可用容量**：14 点扫描中 KV token 容量从 2,898,432 降到 1,888,332（−34.8%），padding 与块大小严格线性（每 +32 token 增 6.04 个百分点，反推 t\*≈530）。
3. **容量不是性能瓶颈，所以上一条是纯亏**：同块大小只换口径，容量 +76.4% 只带来吞吐 +2.1%。
4. **有复用负载的收益由命中几何决定**：命中 = `floor(前缀/块)×块`；前缀 1024 下命中率 26.6% → 42.0% → 55.2%，TTFT 降 22.8% 与 prefill 计算量降 22.6% 吻合。换前缀长度结论会变，前缀小于块大小时命中归零。
5. **块内复用当前无效**：默认与 unit=16 命中逐字节相同（0/58,370 与 26,112/96,768）。机制是协调器按组取交集，Mamba 检查点仍在 544 边界。
6. **块大小不随模型规模单调**：2B 是 544、9B 是 528，只差一个 16 的对齐单位。
