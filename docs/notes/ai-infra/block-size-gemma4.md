# Gemma 4 的 block size 实测

> 模型：`google/gemma-4-26B-A4B-it`（25.8B / MoE，30 层 = **25 层滑窗 + 5 层全注意力**，滑窗 1024，`attention_k_eq_v`）。
> 环境：A800-80GB 单卡，vLLM 0.32.0，bf16。后端是 **Triton**（head_dim 异构 256/512，FA4 不可用）。

## 一、块大小可以自由取

没有线性/Mamba 层，不走块大小推导，`--block-size` 原样生效：

| 传入 | 实际生效 | `kv lcm block sizes` |
|---:|---:|---|
| 16 | 16 | 32 |
| 32 | 32 | 64 |
| 64 | 64 | 128 |
| 128 | 128 | 256 |
| 256 | 256 | 512 |
| 512 | 512 | 1024 |
| 1024 | 1024 | 2048 |
| 2048 | 2048 | 4096 |
| 4096 | 4096 | 8192 |
| 6144 | 6144 | 12288 |

两条规律：

1. **统一页大小恒为块大小的 2 倍**（滑窗组 head_dim 256、全局组 512，跨组对齐）；
2. **块 ≥1024 必须关掉 CUDA graph**：图的显存 profiling 需要一份正比于块大小的临时 KV（1024→20 GiB、2048→40 GiB、4096→80 GiB、6144→120 GiB），26B 权重已占 48.4 GiB，装不下。关掉后 6144 正常启动。

## 二、可用容量：块越大越亏，且没有 Mamba 也一样

固定 10 GiB KV 预算、`--enforce-eager`，10 档扫描：

| 块大小 | KV token | 相对 32 |
|---:|---:|---:|
| 16 | 47,620 | 1.001 |
| 32 | 47,578 | 1.000 |
| 64 | 47,493 | 0.998 |
| 128 | 47,326 | 0.995 |
| 256 | 46,995 | 0.988 |
| 512 | 46,345 | 0.974 |
| 1024 | 45,100 | 0.948 |
| 2048 | 42,799 | 0.900 |
| 4096 | 38,836 | 0.816 |
| 6144 | 31,278 | **0.657** |

**块 32 → 6144，可用容量 −34.3%。** 与 Qwen3.5-2B 混合模型的 −34.8% 几乎一致——说明"块越大越亏容量"主要来自**块超过滑窗宽度后的页内浪费**，不是 Mamba padding 独有。

## 三、端到端：TTFT 略升，TPOT 一动不动

### CUDA graph 模式（生产口径）

| 块大小 | 并发 1 TTFT | 并发 1 TPOT | 并发 32 吞吐 | 并发 32 TTFT |
|---:|---:|---:|---:|---:|
| 16 | 217.9 ms | 8.14 ms | 3.35 req/s | 1,167 ms |
| 64 | 220.7 | 8.23 | 2.82 | 1,795 |
| 128 | 219.0 | 8.15 | **3.40** | 1,706 |
| 256 | 223.9 | 8.10 | 3.41 | 1,802 |
| 512 | 234.2 | 8.25 | 3.34 | 1,911 |
| 1024 | 255.3 | 8.16 | — | — |

**128 → 1024：TTFT +16.6%，TPOT +0.1%，并发吞吐 −1.8%。**

注意 16/64 的 TTFT 与 128 基本一样（217.9 / 220.7 / 219.0），**说明 128 以下再减小没有收益**。

### eager 模式（可比口径，7 档全扫）

| 块大小 | 并发 1 TTFT | 并发 1 TPOT |
|---:|---:|---:|
| 128 | 268.7 ms | 54.47 ms |
| 256 | 271.0 | 56.00 |
| 512 | 271.4 | 56.48 |
| 1024 | 287.2 | 54.78 |
| 2048 | 311.0 | 54.47 |
| 4096 | 314.1 | 54.29 |
| 6144 | 314.6 | 54.89 |

TTFT +17.1%（2048 后饱和），TPOT 无趋势。**eager 与 graph 的绝对量级差 6.7 倍**（TPOT 54.5 vs 8.15 ms），所以 eager 只能看相对趋势。

### 长输入（16384，graph）

| 块大小 | TTFT | TPOT |
|---:|---:|---:|
| 128 | 1,156.1 ms | 9.09 ms |
| 512 | 1,179.9 | 9.13 |

16K 输入下同样 TTFT +2.1%、TPOT +0.4%。

## 四、并发吞吐的损失来自容量，不是块本身

同一比较（并发 32、160 请求、eager），只改 KV 预算：

| 块大小 | 10 GiB 预算 | 20 GiB 预算 | graph（110k token） |
|---:|---:|---:|---:|
| 128 | 2.15 req/s | 3.17 | 3.40 |
| 1024 | 1.57（−27%） | 3.13（−1.3%） | — |
| 4096 | 0.58（−73%） | 2.23（−30%） | — |

**预算从 10 → 20 GiB，128→1024 的损失从 −27% 缩到 −1.3%**。容量一旦充足，块大小对吞吐几乎无影响。

## 五、注意力 kernel：prefill +600%，decode 0%

离线 `torch.profiler` 抓 `kernel_unified_attention`（必须设 `VLLM_ENABLE_V1_MULTIPROCESSING=0`，否则引擎在子进程、抓不到 kernel）：

| 块大小 | prefill p50 | prefill p99 | decode p50 | decode p99 |
|---:|---:|---:|---:|---:|
| 128 | 0.846 ms | 3.016 ms | 0.0134 ms | 0.0171 ms |
| 256 | 1.838 | 6.076 | 0.0134 | 0.0171 |
| 512 | 3.833 | 10.988 | 0.0134 | 0.0171 |
| 1024 | 5.927 | 15.362 | 0.0134 | 0.0171 |
| 2048 | 5.925 | 15.314 | 0.0134 | 0.0171 |
| 4096 | 5.924 | 15.351 | 0.0134 | 0.0171 |

- **prefill：128 → 1024 单调上升（p50 +600%），1024 后完全饱和**；
- **decode：六档一模一样（13.4 µs）**，只有 0.009/0.013/0.017 三个离散值；
- **双峰 = 25 滑窗层 vs 5 全局层**：CDF 在 0.833（=25/30）处有台阶，全局层是滑窗层的 2.6–3.6 倍。

机制推测（有数据支持、待源码确认）：页大小超过滑窗宽度（1024）后，滑窗层无法跳过窗口外的页，只能按整页计算，prefill 计算量从约 1024 token 膨胀到整段；超过 1024 后页无法再变粗，故饱和。

## 六、结论

| 维度 | 128 → 4096 的变化 |
|---|---|
| TTFT | +16.6%（graph，到 1024）/ +17.1%（eager，到 6144） |
| **TPOT** | **0%**（decode kernel 恒定 13.4 µs） |
| 并发吞吐 | 容量充足时 −2%；容量紧张时 −27%~−73% |
| 可用容量 | −18%（47,326 → 38,836 token） |
| **prefill attention kernel** | **+600%**（1024 后饱和） |
| decode attention kernel | **0%** |

**块大小在 Gemma 4 上是"预热成本 + 显存"两个维度的参数，对解码毫无影响；调大只亏容量、并让 prefill 注意力慢约 7 倍。**

## 七、已知缺口

| 项 | 说明 |
|---|---|
| 6144 的 prefill kernel | 三次尝试仍被拆成 2 批（n=60），与 chunked prefill 的批预算（8192）加块 6144 页粒度有关，暂不能与其余档比较 |
| 块 32 的 graph 模式 | 多轮启动失败，未定位 |
| 16 / 64 的 eager 模式 | 服务请求时引擎崩溃（同一参数 graph 模式正常），属小页在 eager 路径上的不稳定 |
| 2048 / 4096 / 6144 的 graph 模式 | 单卡放不下（图缓冲需 40/80/120 GiB），需 TP=4 |
