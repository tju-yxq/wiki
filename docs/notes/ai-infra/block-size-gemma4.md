# SWA/Full 模型 block size 实测

> 状态：**主体已完成**。块大小可取值、显存代价、端到端 TTFT/TPOT、并发吞吐、注意力内核分布均已实测。
> 环境：A800-80GB 单卡，vLLM 0.32.0，bf16，`google/gemma-4-26B-A4B-it`。
> 第二篇汇报，第一篇（混合注意力模型）见 [混合注意力 block size 实测](/notes/ai-infra/block-size-weekly)。

## 一、本周汇报三件事

| # | 问题 | 状态 |
|---|---|---|
| 1 | 纯注意力模型上，块大小能不能自由取 | ✅ 已定论：16–6144 全部原样生效 |
| 2 | 块调大后，显存与性能各差多少 | ✅ 已实测：容量 −34.3%，首字 +16.6%，解码 0% |
| 3 | 注意力计算本身受影响吗 | ✅ 已实测：prefill 慢 7 倍，decode 不变 |

## 二、实验设置：模型与口径

### 环境与模型

| 项 | 值 |
|---|---|
| 硬件 | 单张 A800-SXM4-80GB（每次只用 1 张） |
| 引擎 | vLLM 0.32.0，PyTorch 2.13.0+cu130，bf16 |
| 模型 | `google/gemma-4-26B-A4B-it`：25.8B MoE（128 experts，激活约 4B） |
| 层结构 | 30 层 = **25 层滑窗（窗口 1024）+ 5 层全注意力** |
| KV 形状 | 滑窗组 8 头 × 256 维；全局组 2 头 × 512 维 |
| 权重 | 51.6 GB（48.4 GiB） |
| 后端 | **Triton**（head_dim 异构，FlashAttention 4 不可用） |
| 必设环境变量 | `FLASHINFER_DISABLE_VERSION_CHECK=1` |

选它的原因：没有线性/Mamba 层，块大小不受状态页推导约束，可以连续取值；同时是滑窗 + 全局的混合结构，对应 SWA/Full 这一类模型。

### 三套口径

同一配置在不同显存口径下结论会相反，因此每张表都标明口径。

| 口径 | 参数 | 显存怎么分 | 用来回答 |
|---|---|---|---|
| 固定字节 | `--kv-cache-memory-bytes 10GiB` | KV 池恒为 10 GiB | 隔离容量，只看块大小本身 |
| 部署 | `--gpu-memory-utilization 0.80 / 0.93 / 0.95` | 吃掉剩余显存，容量随块浮动 | 真实部署会怎样 |
| eager / graph | `--enforce-eager` 开 / 关 | CUDA graph 开关 | graph 是生产口径，eager 让大块能起来 |

### 指标与每格流程

| 指标 | 含义 |
|---|---|
| TTFT | 首个 token 到达时间，主要由 prefill 决定 |
| TPOT | 后续每 token 平均生成时间，反映解码速度 |
| KV token 容量 | 启动日志 `GPU KV cache size`，池子能驻留多少 token |
| padding | 页内浪费比例 |

每格流程：起服务 → 等健康检查 → **核对实际生效块大小** → 跑一轮热身（丢弃结果）→ 正式压测 → 记录指标 → 关服务。

热身不能省：不加热身时块 128 测出 TTFT 5,951 ms、块 256 只有 327 ms，差 18 倍，那是 Triton 内核首次编译开销，不是块大小效应。加热身之后两者是 268.7 / 271.0 ms。

## 三、块大小能不能自由取

逐档传 `--block-size`，只启动服务读启动日志，不压测。

| 传入 | 实际生效 | `kv lcm block sizes` |
|---:|---:|---|
| 16 | 16 | 32 |
| 32 | 32 | 64 |
| 64 | 64 | 128 |
| 128 | 128 | 256 |
| 256 | 256 | 512 |
| 512 | 512 | 1024 |
| 1024 | 1024 | 2048 |
| 2048 | 2048 | 4096 |
| 4096 | 4096 | 8192 |
| 6144 | 6144 | 12288 |

三点结论：

1. **传入值就是生效值**，没有推导约束。对比第一篇 Qwen3.5-2B 传 256 会被抬到 768，这里不会。
2. **统一页恒为块大小的 2 倍**。两组 KV 形状不同（滑窗 8 头 × 256、全局 2 头 × 512），页大小要取两组对齐的最小公倍数，所以实际占显存的页比传入值大一倍。
3. **块 ≥1024 必须关掉 CUDA graph**，否则起不来：

| 块大小 | CUDA graph 录制需要的临时 KV |
|---:|---:|
| 1024 | 20 GiB |
| 2048 | 40 GiB |
| 4096 | 80 GiB |
| 6144 | 120 GiB |

权重已占 48.4 GiB，单卡 80 GB 剩不到 32 GiB，所以 1024 以上开图必 OOM。关掉后 6144 能正常启动，**说明 vLLM 支持 6144，限制来自显存**。

## 四、已实测：块变大 → 可用容量下降

**测量方式**：固定 `--kv-cache-memory-bytes 10GiB`，让每档拿到完全相同的 KV 字节预算，只改块大小，读启动日志。

![容量随块大小下降](</img/g4/fig1_capacity.png>)

| 块大小 | 能装多少 token | 相对 32 |
|---:|---:|---:|
| 16 | 47,620 | 1.001 |
| 32 | 47,578 | 1.000 |
| 64 | 47,493 | 0.998 |
| 128 | 47,326 | 0.995 |
| 256 | 46,995 | 0.988 |
| 512 | 46,345 | 0.974 |
| 1024 | 45,100 | 0.948 |
| 2048 | 42,799 | 0.900 |
| 4096 | 38,836 | 0.816 |
| 6144 | 31,278 | **0.657** |

三条结论：

1. 同样的 10 GiB，块 32 装 47,578 token，块 6144 只装 31,278，**少 34.3%**；
2. 下滑集中在块 >1024 之后，因为**块一旦超过滑窗宽度 1024，滑窗层就用不满整页**——块 2048 时一页只用一半，块 6144 时一页只用六分之一；
3. 对比第一篇：Qwen3.5-2B 混合模型掉 34.8%，这里纯注意力掉 34.3%，几乎一样。**"块越大越亏容量"不是 Mamba 独有的问题**，根源是块超过有效上下文长度后的页内浪费。

## 五、已实测：块变大对端到端性能的影响

### CUDA graph 模式（生产口径，输入 4096 / 输出 128）

![TTFT 与 TPOT 随块大小的变化](</img/g4/fig2_e2e.png>)

| 块大小 | 并发 1 TTFT | 并发 1 TPOT | 并发 32 吞吐 |
|---:|---:|---:|---:|
| 16 | 217.9 ms | 8.14 ms | 3.35 req/s |
| 64 | 220.7 ms | 8.23 ms | 2.82 req/s |
| 128 | 219.0 ms | 8.15 ms | 3.40 req/s |
| 256 | 223.9 ms | 8.10 ms | 3.41 req/s |
| 512 | 234.2 ms | 8.25 ms | 3.34 req/s |
| 1024 | 255.3 ms | 8.16 ms | — |

结论：

1. **TPOT 完全没有趋势**（8.10–8.25，波动 <2%）：块大小怎么改，解码速度都一样；
2. **TTFT 从 217.9 涨到 255.3**（128 → 1024，+16.6%），单调上升；
3. **16 和 64 的 TTFT 与 128 几乎一致**，说明减到 128 以下没有额外收益；
4. 并发吞吐 3.34–3.41 基本持平（64 那档 2.82 是当时卡上有别人任务，属噪声）。

### eager 模式（7 档全扫，仅看相对差异）

| 块大小 | 并发 1 TTFT | 并发 1 TPOT |
|---:|---:|---:|
| 128 | 268.7 ms | 54.47 ms |
| 256 | 271.0 ms | 56.00 ms |
| 512 | 271.4 ms | 56.48 ms |
| 1024 | 287.2 ms | 54.78 ms |
| 2048 | 311.0 ms | 54.47 ms |
| 4096 | 314.1 ms | 54.29 ms |
| 6144 | 314.6 ms | 54.89 ms |

TTFT +17.1%（涨幅集中在 512→2048，之后平掉），TPOT 无趋势。

### 为什么 eager 的绝对值不能用

| 指标（块 128，并发 1） | eager | CUDA graph | 倍率 |
|---|---:|---:|---:|
| TPOT | 54.47 ms | **8.15 ms** | graph 快 6.7× |
| TTFT | 268.7 ms | **219.0 ms** | graph 快 18.5% |

CUDA graph 把"发射 30 层算子"录制成一次调用，省掉每 token 数百次内核启动。解码每步都走一遍，受益最大；prefill 只走一次，受益小。这个差异足以淹没块大小的效应，所以**绝对性能只看 graph 数据，eager 只作相对比较**。

### 长输入（16384 token，graph）

| 块大小 | TTFT | TPOT |
|---:|---:|---:|
| 128 | 1,156.1 ms | 9.09 ms |
| 512 | 1,179.9 ms | 9.13 ms |

16K 输入下块 128 → 512 只涨 2.1% / 0.4%，比短输入更不敏感。

## 六、已实测：并发吞吐的下跌是容量造成的

同样固定 10 GiB、并发 32、160 请求，先看现象：

| 块大小 | 吞吐 |
|---:|---:|
| 128 | 2.15 req/s |
| 1024 | 1.57（−27%） |
| 4096 | 0.58（**−73%**） |

看起来"块越大吞吐越差"。把 KV 预算提到 20 GiB 再测一遍：

![不同显存预算下的并发吞吐](</img/g4/fig3_budget.png>)

| 块大小 | 10 GiB 预算 | 20 GiB 预算 |
|---:|---:|---:|
| 128 | 2.15 | 3.17 |
| 1024 | 1.57（−27%） | **3.13（−1.3%）** |
| 4096 | 0.58（−73%） | **2.23（−30%）** |

再用 graph 口径（容量 110k token）验证：128 / 256 / 512 的吞吐是 3.40 / 3.41 / 3.34，只差 1.8%。

三组数据一致：**同样的块，只要给够显存，损失从 −27% 缩到 −1.3%。容量充足时块大小对并发吞吐几乎无影响，看起来的损失全部来自"块大 → 容量小 → 请求排队"。**

## 七、已实测：注意力内核 prefill 慢 7 倍、decode 不变

**为什么单独测内核**：端到端是所有算子之和，这是 MoE 模型，路由、专家矩阵乘、归一化都在抢时间，注意力可能只占一小部分，必须摘出来看。

**方法**：`torch.profiler` 录 CUDA 活动，过滤 `kernel_unified_attention`，分两阶段采样：

| 阶段 | 负载 | 样本数 |
|---|---|---|
| prefill | 8 条 × 4000 token，只生成 1 token | 30（30 层 × 1 次前向） |
| decode | 8 条短 prompt，生成 96 token | 2,880（30 层 × 96 步） |

两个坑：引擎必须与 profiler 同进程（设 `VLLM_ENABLE_V1_MULTIPROCESSING=0`），否则抓到空壳；不能把 `reshape_and_cache`（写 KV，不是注意力计算）算进来，混进去会把 p50 拉低一半。

![prefill 与 decode 的注意力内核 CDF](</img/g4/fig4_cdf.png>)

| 块大小 | prefill p50 | prefill p99 | decode p50 | decode p99 |
|---:|---:|---:|---:|---:|
| 128 | **0.846 ms** | **3.016 ms** | 0.0134 ms | 0.0171 ms |
| 256 | 1.838 | 6.076 | 0.0134 | 0.0171 |
| 512 | 3.833 | 10.988 | 0.0134 | 0.0171 |
| 1024 | 5.927 | 15.362 | 0.0134 | 0.0171 |
| 2048 | 5.925 | 15.314 | 0.0134 | 0.0171 |
| 4096 | 5.924 | 15.351 | 0.0134 | 0.0171 |

三条结论：

1. **prefill 内核从 0.846 涨到 5.927 ms，慢 7 倍（+600%），1024 后完全饱和**。与端到端 TTFT 只有 +17% 不矛盾：注意力只占 prefill 总时间一小部分，这个事实在端到端指标里被稀释了。
2. **decode 内核六档一模一样，都是 13.4 µs**。这解释了 TPOT 为什么完全不动：每步只处理 1 个新 token，页大小只影响一次页表查找。
3. **CDF 在 25/30 = 0.833 处有台阶**，这是 25 层滑窗与 5 层全局的分界：

| 块大小 | 滑窗层（25 个） | 全局层（5 个） | 倍数 |
|---:|---:|---:|---:|
| 128 | 0.846 ms | 3.009 ms | 3.56× |
| 512 | 3.832 ms | 10.970 ms | 2.86× |
| 4096 | 5.922 ms | 15.324 ms | 2.59× |

**表里的 p50 其实是滑窗层，p99 是全局层**；全局层慢 2.6–3.6 倍，因为它的头维度是 512（滑窗层 256）。

prefill 越来越慢的机制（**待源码级确认**）：滑窗层本来可以跳过窗口外的页，但当页粒度超过窗口大小后，一页里既有窗口内也有窗口外数据，没法整页跳过，只能按整页算；块超过 1024 后页无法再变粗，所以饱和。

## 八、数据取舍与还缺什么

### 采用的数据

| 数据集 | 格数 | 采集条件 |
|---|---|---|
| 块大小口径确认 | 10 档（16–6144） | 只读启动日志 |
| 容量曲线 | 10 点 | 固定 10 GiB，单卡独占窗口 |
| 端到端 graph | 6 档 × 并发 1/32 | util 0.93–0.95，无争抢 |
| 端到端 eager | 7 档 × 并发 1/32 | 统一关闭 CUDA graph |
| 并发吞吐对照 | 3 档 × 三套预算 | 同负载、同并发 |
| 注意力内核 | 6 档 × 2 阶段 | 离线 profiler，样本 30 / 2880 |

### 弃用的数据

| 数据 | 原因 |
|---|---|
| 首版未热身的小块数据 | 块 128 测出 TTFT 5,951 ms，是 Triton 首次编译开销，非块大小效应 |
| graph 模式 2048/4096/6144 | 图录制需 40/80/120 GiB，单卡放不下 |
| 6144 的 prefill 内核 | 三次尝试都被拆成 2 批（样本 60 而非 30），与 chunked prefill 批预算 8192 + 块 6144 页粒度有关 |
| 块 32 的 graph 模式 | 多轮启动失败，未定位 |
| 16 / 64 的 eager 模式 | 服务一接请求引擎退出（同参数 graph 正常） |

### 还缺什么

| 实验 | 状态 | 备注 |
|---|---|---|
| 6144 纳入内核趋势 | 未解决 | 需改 profiling 设计（单条 prompt 或调大批预算） |
| 2048 以上的 graph 模式 | 单卡不可行 | 需 TP=4 |
| 重复实验（n≥3） | 未做 | 每格 n=1，判断差异时 2–3% 以内应视为噪声 |
| 多卡行为（TP=2/4） | 未测 | 未验证并行度对块大小效应的影响 |

## 九、结论与剩余

### 有效数据给出的六条结论

1. **块大小可以自由取**：16–6144 全部原样生效，不受推导约束；统一页恒为块大小的 2 倍。
2. **块 ≥1024 必须关 CUDA graph**：图录制要 20–120 GiB 临时 KV，单卡放不下；关掉后 6144 能跑，说明限制来自显存而非引擎。
3. **块变大主要亏容量**：固定 10 GiB 下 47,578 → 31,278 token（−34.3%），下滑点在滑窗宽度 1024 之后。
4. **端到端只有首字变慢**：TTFT +16.6%（graph 到 1024），**TPOT 完全不变**（8.10–8.25 ms）。
5. **并发吞吐的损失来自容量**：10 GiB 下掉 27%~73%，20 GiB 下只掉 1.3%~30%，容量充足时只差 1.8%。
6. **注意力内核 prefill 慢 7 倍、decode 不变**：prefill p50 0.846 → 5.927 ms（1024 后饱和），decode 恒为 13.4 µs；CDF 的台阶对应 25 层滑窗与 5 层全局。

### 剩余工作

| 项 | 说明 |
|---|---|
| 6144 的内核数据 | 需改 profiling 设计，目前不可比 |
| graph 模式的 2048 以上 | 需 TP=4 才能提供 40 GiB 以上的图缓冲 |
| 重复实验与置信区间 | 现在是每格 n=1 |
| 多卡行为 | TP=2/4 下的块大小效应未验证 |
