# SWA/Full 模型 block size 实测

> 状态：**主体已完成**。块大小可取值、显存代价、端到端 TTFT/TPOT、并发吞吐、注意力内核分布均已实测。
> 环境：A800-80GB 单卡，vLLM 0.32.0，bf16，`google/gemma-4-26B-A4B-it`。
> 这是第二篇周会汇报，第一篇（混合注意力模型）见 [混合注意力 block size 实测](/notes/ai-infra/block-size-weekly)。

## 一、本周汇报三件事

| # | 问题 | 结论 | 状态 |
|---|---|---|---|
| 1 | 纯注意力模型上，块大小能不能自由取 | 16–6144 全部原样生效，不受推导约束；但 ≥1024 必须关掉 CUDA graph | ✅ 已定论 |
| 2 | 调大块，代价有多大 | 可用容量 **−34.3%**，首字延迟 **+16.6%**，解码 **0%** | ✅ 已实测 |
| 3 | 注意力计算本身受影响吗 | prefill 内核慢 **7 倍**（1024 后饱和），decode 内核 **完全不变** | ✅ 已实测 |

## 三、实验设置与口径

### 环境与模型

| 项 | 值 |
|---|---|
| 硬件 | 单张 A800-SXM4-80GB（每次只用 1 张） |
| 引擎 | vLLM 0.32.0，PyTorch 2.13.0+cu130，bf16 |
| 模型 | `google/gemma-4-26B-A4B-it`：25.8B MoE（128 experts），**25 层滑窗（窗口 1024）+ 5 层全注意力**，权重 51.6 GB |
| 后端 | **Triton**（两组 head_dim 分别为 256 / 512，FlashAttention 4 不可用） |
| 必设环境变量 | `FLASHINFER_DISABLE_VERSION_CHECK=1` |

**为什么选这个模型：** 它没有线性/Mamba 层，块大小不受"Mamba 状态页"推导约束，可以连续取值；同时是滑窗 + 全局的混合结构，正好对应 SWA/Full 这一类模型。

### 三套口径（同一配置结果可能相反，必须分开看）

| 口径 | 参数 | 显存怎么分 | 用来回答 |
|---|---|---|---|
| 固定字节 | `--kv-cache-memory-bytes 10GiB` | KV 池恒为 10 GiB | 隔离容量，只看块大小本身 |
| 部署 | `--gpu-memory-utilization 0.80 / 0.93 / 0.95` | 吃掉剩余显存，容量随块浮动 | 真实部署会怎样 |
| eager / graph | `--enforce-eager` 开 / 关 | CUDA graph 开关 | graph 是生产口径，eager 只是为了让大块能起来 |

### 指标与每格流程

| 指标 | 含义 |
|---|---|
| TTFT | 首个 token 的到达时间，主要由 prefill 决定 |
| TPOT | 后续每个 token 的平均生成时间，反映解码速度 |
| KV token 容量 | 启动日志 `GPU KV cache size`，池子能驻留多少 token |
| padding | 页内浪费比例 |

每格流程：起服务 → 等健康检查 → **从日志核对实际生效块大小** → 跑一轮热身（丢弃结果）→ 正式压测 → 记录指标 → 关服务。

> 热身不能省：不加热身时块 128 测出 TTFT 5,951 ms、块 256 只有 327 ms，差 18 倍——那是 Triton 内核首次编译的开销，不是块大小的效应。加热身之后两者是 268.7 / 271.0 ms。

## 四、块大小能取哪些值

| 传入 | 实际生效 | `kv lcm block sizes` |
|---:|---:|---|
| 16 | 16 | 32 |
| 32 | 32 | 64 |
| 64 | 64 | 128 |
| 128 | 128 | 256 |
| 256 | 256 | 512 |
| 512 | 512 | 1024 |
| 1024 | 1024 | 2048 |
| 2048 | 2048 | 4096 |
| 4096 | 4096 | 8192 |
| 6144 | 6144 | 12288 |

两点解读：

1. **前两列完全相同**，说明块大小原样生效。对比第一篇里 Qwen3.5-2B 传 256 会被抬到 768（Mamba 状态页反解出下界），这里没有这个约束。
2. **统一页恒为块大小的 2 倍**。因为两组 KV 形状不同（滑窗 8 头 × 256，全局 2 头 × 512），页大小要取两组对齐的最小公倍数。**实际占显存的页比你传入的块大小大一倍。**

### 一个前提：块 ≥1024 必须关 CUDA graph

CUDA graph 录制前要预估显存，会临时申请正比于块大小的 KV：

| 块大小 | 图录制需要的临时 KV |
|---:|---:|
| 1024 | 20 GiB |
| 2048 | 40 GiB |
| 4096 | 80 GiB |
| 6144 | 120 GiB |

权重已占 48.4 GiB，单卡 80 GB 剩不到 32 GiB，所以 1024 以上开图必 OOM。关掉后 6144 能正常启动——**说明 vLLM 支持 6144，限制来自显存**。

## 五、代价一：显存（容量曲线）

| 块大小 | 能装多少 token | 相对 32 |
|---:|---:|---:|
| 16 | 47,620 | 1.001 |
| 32 | 47,578 | 1.000 |
| 64 | 47,493 | 0.998 |
| 128 | 47,326 | 0.995 |
| 256 | 46,995 | 0.988 |
| 512 | 46,345 | 0.974 |
| 1024 | 45,100 | 0.948 |
| 2048 | 42,799 | 0.900 |
| 4096 | 38,836 | 0.816 |
| 6144 | 31,278 | **0.657** |

同样 10 GiB，块 32 装 47,578 token，块 6144 只装 31,278，**少了 34.3%**。

**原因在滑窗宽度 1024。** 25 层滑窗层每层只需最近 1024 个 token，但内存按整页分：

- 块 128：1024 token 正好 8 页，每页装满；
- 块 2048：一页 2048 槽位，滑窗只用前 1024 个，**一半空着**；
- 块 6144：一页 6144 槽位，只用 1024 个，**浪费 6 倍**。

对比第一篇：Qwen3.5-2B 是混合模型掉 34.8%，这里是纯注意力掉 34.3%，几乎一样。**所以"块越大越亏容量"的根源是"块超过有效上下文长度后的页内浪费"，不是 Mamba 独有。**

## 六、代价二：首字延迟（TTFT）与解码（TPOT）

### CUDA graph 模式（生产口径，输入 4096 / 输出 128）

| 块大小 | 并发 1 TTFT | 并发 1 TPOT | 并发 32 吞吐 |
|---:|---:|---:|---:|
| 16 | 217.9 ms | 8.14 ms | 3.35 req/s |
| 64 | 220.7 ms | 8.23 ms | 2.82 req/s |
| 128 | 219.0 ms | 8.15 ms | 3.40 req/s |
| 256 | 223.9 ms | 8.10 ms | 3.41 req/s |
| 512 | 234.2 ms | 8.25 ms | 3.34 req/s |
| 1024 | 255.3 ms | 8.16 ms | — |

- **TPOT 那一列没有任何趋势**（8.10–8.25，波动 <2%）：块大小怎么改，解码速度都一样。
- **TTFT 从 217.9 涨到 255.3**（128 → 1024，+16.6%），单调上升。
- **16 和 64 的 TTFT 与 128 几乎一致**，说明减到 128 以下没有额外收益。
- 吞吐 3.34–3.41 基本持平（64 那档 2.82 是当时 GPU 上有别人任务，属噪声）。

### eager 模式（7 档全扫，仅看相对差异）

| 块大小 | 并发 1 TTFT | 并发 1 TPOT |
|---:|---:|---:|
| 128 | 268.7 ms | 54.47 ms |
| 256 | 271.0 ms | 56.00 ms |
| 512 | 271.4 ms | 56.48 ms |
| 1024 | 287.2 ms | 54.78 ms |
| 2048 | 311.0 ms | 54.47 ms |
| 4096 | 314.1 ms | 54.29 ms |
| 6144 | 314.6 ms | 54.89 ms |

TTFT +17.1%（涨幅集中在 512→2048，之后平掉），TPOT 无趋势。

### 为什么 eager 绝对值不能用

| 指标（块 128，并发 1） | eager | CUDA graph | 倍率 |
|---|---:|---:|---:|
| TPOT | 54.47 ms | **8.15 ms** | graph 快 6.7× |
| TTFT | 268.7 ms | **219.0 ms** | graph 快 18.5% |

CUDA graph 把"发射 30 层算子"录制成一次调用，省掉每个 token 数百次内核启动。解码每步都走一遍，受益最大；prefill 只走一次，受益小。**这个差异足以淹没块大小的效应，所以绝对性能只看 graph 数据。**

### 长输入（16384 token，graph）

| 块大小 | TTFT | TPOT |
|---:|---:|---:|
| 128 | 1,156.1 ms | 9.09 ms |
| 512 | 1,179.9 ms | 9.13 ms |

16K 输入下块 128 → 512 只涨 2.1% / 0.4%，比短输入更不敏感。

## 七、并发吞吐：看起来掉 73%，其实是容量

**图 3：不同显存预算下的并发吞吐**

![不同显存预算下的并发吞吐](</img/g4/fig3_budget.png>)

先看现象（固定 10 GiB、并发 32、160 请求）：

| 块大小 | 吞吐 |
|---:|---:|
| 128 | 2.15 req/s |
| 1024 | 1.57（−27%） |
| 4096 | 0.58（**−73%**） |

再看同配置换 20 GiB 预算：

| 块大小 | 10 GiB | 20 GiB |
|---:|---:|---:|
| 128 | 2.15 | 3.17 |
| 1024 | 1.57（−27%） | **3.13（−1.3%）** |
| 4096 | 0.58（−73%） | **2.23（−30%）** |

**同样的块，只要给够显存，损失从 −27% 缩到 −1.3%。** 再用 graph 口径（容量 110k token）验证：128 / 256 / 512 的吞吐是 3.40 / 3.41 / 3.34，只差 1.8%。

三组数据一致：**容量充足时块大小对并发吞吐几乎无影响；看起来的损失全部来自"块大 → 容量小 → 请求排队"。**

## 八、注意力内核：prefill 慢 7 倍、decode 不变

### 为什么要单独看内核

端到端是"所有算子加起来"的结果。这是 MoE 模型，路由、专家矩阵乘、归一化、位置编码都在抢时间，注意力可能只占一小部分。**要判断块大小有没有真的改变注意力计算，必须把它单独摘出来。**

做法：用 `torch.profiler` 录 CUDA 活动，过滤出 `kernel_unified_attention`，分两个阶段采样：

| 阶段 | 负载 | 样本数 |
|---|---|---|
| prefill | 8 条 × 4000 token，只生成 1 token | 30（30 层 × 1 次前向） |
| decode | 8 条短 prompt，生成 96 token | 2,880（30 层 × 96 步） |

两个坑：**引擎必须与 profiler 同进程**（设 `VLLM_ENABLE_V1_MULTIPROCESSING=0`），否则抓到的是空壳；**不能把 `reshape_and_cache` 算进来**，它负责写 KV 不是注意力计算，混进去会把 p50 拉低一半。

**图 4：注意力内核耗时 CDF**

![prefill 与 decode 的注意力内核 CDF](</img/g4/fig4_cdf.png>)

| 块大小 | prefill p50 | prefill p99 | decode p50 | decode p99 |
|---:|---:|---:|---:|---:|
| 128 | **0.846 ms** | **3.016 ms** | 0.0134 ms | 0.0171 ms |
| 256 | 1.838 | 6.076 | 0.0134 | 0.0171 |
| 512 | 3.833 | 10.988 | 0.0134 | 0.0171 |
| 1024 | 5.927 | 15.362 | 0.0134 | 0.0171 |
| 2048 | 5.925 | 15.314 | 0.0134 | 0.0171 |
| 4096 | 5.924 | 15.351 | 0.0134 | 0.0171 |

三条读法：

1. **prefill 内核从 0.846 涨到 5.927，慢 7 倍（+600%），1024 后完全饱和。** 与端到端 TTFT 只有 +17% 不矛盾——注意力只占 prefill 总时间一小部分，但这个事实在端到端指标里被稀释了。
2. **decode 内核六档一模一样，都是 13.4 µs。** 这解释了 TPOT 为什么完全不动：每步只处理 1 个新 token，页大小只影响一次页表查找。
3. **CDF 在 25/30 = 0.833 处有台阶**，这是 25 层滑窗与 5 层全局的分界：

| 块大小 | 滑窗层（25 个） | 全局层（5 个） | 倍数 |
|---:|---:|---:|---:|
| 128 | 0.846 ms | 3.009 ms | 3.56× |
| 512 | 3.832 ms | 10.970 ms | 2.86× |
| 4096 | 5.922 ms | 15.324 ms | 2.59× |

**所以表里的 p50 其实是滑窗层，p99 是全局层。** 全局层慢 2.6–3.6 倍，因为它的头维度是 512（滑窗层 256）。

prefill 越来越慢的机制（**待源码级确认**）：滑窗层本来可以跳过窗口外的页，但**当页粒度超过窗口大小后，一页里既有窗口内也有窗口外的数据，没法整页跳过**，只能按整页算；块超过 1024 后页无法再变粗，所以饱和。

## 九、结论

| 维度 | 128 → 4096 的变化 | 结论强度 |
|---|---|---|
| **TPOT（解码）** | **0%**（decode 内核恒定 13.4 µs） | 强，两种模式一致 |
| **TTFT（首字）** | +16.6%（graph 到 1024）/ +17.1%（eager 到 6144） | 强，2048 后饱和 |
| **并发吞吐** | 容量充足时 −2%；容量紧张时 −27%~−73% | 强，三组对照一致 |
| **可用容量** | −18%（47,326 → 38,836 token） | 强 |
| **prefill 注意力内核** | **+600%**（1024 后饱和） | 强，6 档 × 30 层 |
| **decode 注意力内核** | **0%** | 强 |

三条实践建议：

1. **别为了性能调大块大小。** 解码不受影响，首字反而更慢，容量还掉三分之一。
2. **块大小主要成本是容量，而容量只在紧张时才咬人。** 显存富余时块大小基本随便选；显存吃紧时小页带来的容量收益很可观。
3. **128 附近是最优区间。** 再小没有额外收益，再大开始亏容量和首字。

## 十、还缺什么

| 项 | 状态 | 说明 |
|---|---|---|
| 6144 的 prefill 内核 | 未解决 | 三次尝试都被拆成 2 批（样本 60 而非 30），与 chunked prefill 批预算 8192 + 块 6144 页粒度有关 |
| 块 32 的 graph 模式 | 未解决 | 多轮启动失败，未定位；eager 下并发 1 能跑（245.7 / 54.11 ms） |
| 16 / 64 的 eager 模式 | 已知不稳定 | 服务一接请求引擎退出（同参数 graph 正常） |
| 2048 以上的 graph 模式 | 单卡不可行 | 图录制需 40 / 80 / 120 GiB，需 TP=4 |
| 重复实验 | 未做 | 每格 n=1，无置信区间；判断差异时 2–3% 以内应视为噪声 |
| 多卡行为 | 未测 | 未验证 TP=2/4 |
