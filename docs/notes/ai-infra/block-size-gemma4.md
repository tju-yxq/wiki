# Gemma 4 的 block size 实测

## 一分钟版结论

如果你只想知道"block size 从 128 调到 6144，性能差多少"，这里是答案：

| 你想知道的 | 答案 | 幅度 |
|---|---|---|
| 解码变快还是变慢 | **完全不变** | TPOT 8.10 → 8.16 ms，±1.8% |
| 首字延迟变好还是变差 | 变差，但有上限 | TTFT 219 → 255 ms（到 1024），+16.6%，之后不再涨 |
| 并发吞吐变好还是变差 | 取决于显存够不够 | 显存充足时 −1.8%；显存紧张时 **−73%** |
| 能装多少上下文 | 明显变少 | 可用 token 容量 **−34.3%** |
| 注意力计算本身 | prefill 变慢、decode 不变 | prefill 单层内核 **+600%**，decode **0%** |

一句话：**在这个模型上，block size 是"显存"和"首字延迟"两个维度的参数，跟解码速度无关。调大只亏容量。**

---

## 一、背景：block size 到底是什么

大模型推理时，已经处理过的上下文要存成 KV cache（键值缓存），后面每生成一个字都要去查它。KV cache 不会一次申请一大块，而是切成固定大小的**页**（page），每页装固定数量的 token。

**block size 就是"一页装多少 token"。**

它之所以会影响性能，有三个途径：

| 途径 | 通俗解释 | 预期影响 |
|---|---|---|
| 分配粒度 | 页越小，申请和回收越细，尾部的浪费越少；页越大，最后那一页装不满就浪费更多 | 页越大 → 可用容量越少 |
| 页表查找 | 页越大，同样长度的上下文需要的页表项越少，调度开销越小 | 页越大 → 略有好处 |
| 内核分块 | 注意力算子在内部按页并行，页大小会改变它的分块方式和每次处理的量 | 页越大 → 内核行为改变（可能变慢） |

这三条方向不同，所以**不能坐在桌前推断，必须实测**。这就是这组实验的目的。

## 二、为什么选 Gemma 4

`google/gemma-4-26B-A4B-it` 有几个特征让它适合做这个问题：

| 特征 | 数值 | 为什么重要 |
|---|---|---|
| 没有线性 / Mamba 层 | 30 层全是注意力 | **block size 不受"Mamba 状态页"的推导约束**，可以自由取任意 16 的倍数（对比 Qwen3.5-2B 只能取 544/768 等少数值） |
| 滑窗层 + 全局层混合 | 25 层滑窗（窗口 1024）+ 5 层全注意力 | 正好是"SWA/Full 混合"结构，能观察两类层的差异 |
| 两个不同的 KV 形状 | 滑窗组 8 头 × 256 维，全局组 2 头 × 512 维 | 两组的页对齐要求不同，会产生"统一页"约束 |
| MoE | 128 experts，激活约 4B | 权重占 48.4 GiB，留给 KV 的显存很紧，能暴露容量问题 |
| 后端是 Triton | head_dim 异构（256 vs 512），FlashAttention 4 不可用 | 内核行为与 FlashAttention 路径不同，需单独说明 |

## 三、实验设置

### 硬件与软件

| 项 | 值 |
|---|---|
| 显卡 | 单张 A800-SXM4-80GB（每次只用 1 张） |
| 引擎 | vLLM 0.32.0，PyTorch 2.13.0+cu130，bf16 |
| 模型 | `google/gemma-4-26B-A4B-it`，权重 51.6 GB（48.4 GiB） |
| 必设环境变量 | `FLASHINFER_DISABLE_VERSION_CHECK=1` |

### 三套口径（这是最容易看错的地方）

同一个块大小，在不同显存口径下结论会完全相反，所以每项实验都标明口径：

| 口径 | 参数 | 显存怎么分 | 用来回答 |
|---|---|---|---|
| **固定字节** | `--kv-cache-memory-bytes 10GiB` | KV 池恒为 10 GiB | 隔离容量，只看"块大小本身"的效应 |
| **部署** | `--gpu-memory-utilization 0.80/0.93/0.95` | 引擎吃掉剩余显存，容量随块大小浮动 | 真实部署会怎样 |
| **eager / graph** | `--enforce-eager` 开 / 关 | 图形捕获（CUDA graph）开关 | graph 是生产口径；eager 是为了能让大块跑起来 |

**eager 与 graph 的差别必须记住：** 关闭 CUDA graph 后，每一步的算子要逐个发射，解码极慢。实测同一配置 TPOT 从 8.15 ms 涨到 54.47 ms，**差 6.7 倍**。所以：

- 看**绝对性能** → 只能看 graph 模式；
- 看**块大小之间的相对差异** → eager 也可以，但必须整组一致。

### 指标定义

| 指标 | 含义 |
|---|---|
| **TTFT** | Time To First Token，从发请求到收到第一个字的时间，主要由 prefill（读入整段输入）决定 |
| **TPOT** | Time Per Output Token，生成每个后续字的平均时间，反映解码速度 |
| **吞吐** | 单位时间完成的请求数或 token 数 |
| **KV token 容量** | 启动日志 `GPU KV cache size: N tokens`，即显存池能同时驻留多少 token 的上下文 |
| **padding** | 页里被浪费的比例（只在有固定大小状态页的模型上出现） |

### 每格的流程

起服务 → 等健康检查 → **从启动日志核对实际生效的块大小** → 先跑一轮热身（结果丢弃，避免内核首次编译污染）→ 正式压测 → 记录指标 → 关服务。

热身这一步很关键：第一版没有热身，块 128 的 TTFT 测出 5,951 ms，块 256 只有 327 ms，差 18 倍——那是 Triton 内核首次调用的编译开销，不是块大小的效应。加了热身之后两者分别是 268.7 和 271.0 ms。

## 四、第一组：块大小能取哪些值

### 做法

逐档传 `--block-size N`，只启动服务读日志，不压测，核对"传入值 → 实际生效值"。

### 结果

| 传入 | 实际生效 | `kv lcm block sizes` |
|---:|---:|---|
| 16 | 16 | 32 |
| 32 | 32 | 64 |
| 64 | 64 | 128 |
| 128 | 128 | 256 |
| 256 | 256 | 512 |
| 512 | 512 | 1024 |
| 1024 | 1024 | 2048 |
| 2048 | 2048 | 4096 |
| 4096 | 4096 | 8192 |
| 6144 | 6144 | 12288 |

### 怎么看这张表

**第一列和第二列完全一样，说明块大小原样生效。** 这与混合模型形成鲜明对比：Qwen3.5-2B 上你传 256，实际会被抬到 768，因为 Mamba 状态页的大小反推出了一个下界。Gemma 4 没有 Mamba，所以没有这个约束。

**第三列"统一页"恒为块大小的 2 倍。** 原因是这个模型有两套不同形状的 KV：

- 滑窗层：8 个 KV 头 × 256 维；
- 全局层：2 个 KV 头 × 512 维。

两组的"每 token 字节数"不同，页大小必须取两者对齐要求的最小公倍数，结果是块大小的 2 倍。**这意味着实际占显存的页比你传的块大小大一倍**，读容量数据时要把这个因素算进去。

### 一个前提条件：块 ≥1024 必须关掉 CUDA graph

CUDA graph 是"把每一步的算子序列录制下来反复播放"的优化。录制前引擎要预估显存，会临时申请一份正比于块大小的 KV：

| 块大小 | CUDA graph 录制需要的临时 KV |
|---:|---:|
| 1024 | 20 GiB |
| 2048 | 40 GiB |
| 4096 | 80 GiB |
| 6144 | 120 GiB |

26B 权重已经占了 48.4 GiB，单卡 80 GB 剩不到 32 GiB，所以 1024 以上开图必然 OOM。关掉图（`--enforce-eager`）后 6144 能正常启动——**这说明 vLLM 本身支持 6144，限制来自显存**。

## 五、第二组：显存代价（容量曲线）

### 做法

固定 `--kv-cache-memory-bytes 10GiB`，让每档拿到**完全相同的 KV 字节预算**，然后只改块大小，读取启动日志里的 `GPU KV cache size`。

**为什么要固定字节：** 如果不固定，引擎会把剩余显存全吃掉，块小的时候拿到的池子更大，于是"块小 → 容量大"里混了两件事，无法归因。固定字节之后，池子一样大，容量的差异才只能由块大小解释。

### 结果

| 块大小 | 能装多少 token | 相对 32 |
|---:|---:|---:|
| 16 | 47,620 | 1.001 |
| 32 | 47,578 | 1.000 |
| 64 | 47,493 | 0.998 |
| 128 | 47,326 | 0.995 |
| 256 | 46,995 | 0.988 |
| 512 | 46,345 | 0.974 |
| 1024 | 45,100 | 0.948 |
| 2048 | 42,799 | 0.900 |
| 4096 | 38,836 | 0.816 |
| 6144 | 31,278 | **0.657** |

### 怎么读

同样的 10 GiB 显存：

- 块 32 时能装 47,578 个 token；
- 块 6144 时只能装 31,278 个，**少了 34.3%**。

也就是说，**把块调大，等于把三分之一的显存扔掉了**。

### 为什么会掉

关键在于**滑窗宽度 1024**。25 层滑窗层每层只需要保留最近 1024 个 token，但内存是按整页分的：

- 块 128：1024 个 token 正好 8 页，每页都装满，没有浪费；
- 块 2048：一个 token 的上下文落到 1 页里，但这页有 2048 个槽位，滑窗只用得上前 1024 个，**另一半是空的**；
- 块 6144：一页 6144 个槽位，滑窗只用 1024 个，**浪费 6 倍**。

这就是曲线在 1024 之后明显加速下滑的原因。**注意：这条规律与 Mamba 无关**——Qwen3.5-2B 是混合模型，掉 34.8%；Gemma 4 是纯注意力，掉 34.3%，几乎一样。所以"块越大越亏容量"的根源是"块超过有效上下文长度后的页内浪费"，不是 Mamba 独有。

## 六、第三组：端到端性能

### 6.1 CUDA graph 模式（生产口径）

负载：输入 4096 token、输出 128 token。

| 块大小 | 并发 1 TTFT | 并发 1 TPOT | 并发 32 吞吐 | 并发 32 TTFT |
|---:|---:|---:|---:|---:|
| 16 | 217.9 ms | 8.14 ms | 3.35 req/s | 1,167 ms |
| 64 | 220.7 ms | 8.23 ms | 2.82 req/s | 1,795 ms |
| 128 | 219.0 ms | 8.15 ms | **3.40 req/s** | 1,706 ms |
| 256 | 223.9 ms | 8.10 ms | 3.41 req/s | 1,802 ms |
| 512 | 234.2 ms | 8.25 ms | 3.34 req/s | 1,911 ms |
| 1024 | 255.3 ms | 8.16 ms | — | — |

**怎么读：**

- 看 **TPOT 那一列**：8.14 / 8.23 / 8.15 / 8.10 / 8.25 / 8.16——上下波动不到 2%，**没有任何趋势**。块大小怎么改，解码速度都一样。
- 看 **TTFT 那一列**：217.9 → 255.3，128 到 1024 涨了 **16.6%**，是单调的。
- 看**吞吐那一列**：3.35 / 2.82 / 3.40 / 3.41 / 3.34——注意 64 那档偏低（2.82）是当次 GPU 上还有别人的任务在跑，属于噪声；其余四档在 3.34–3.41 之间，**基本持平**。
- 一个意外发现：**16 和 64 的 TTFT（217.9 / 220.7）与 128（219.0）几乎一样**。说明块大小减到 128 以下**没有任何额外收益**，128 就是实际的下限。

### 6.2 eager 模式（可比口径，7 档全扫）

| 块大小 | 并发 1 TTFT | 并发 1 TPOT |
|---:|---:|---:|
| 128 | 268.7 ms | 54.47 ms |
| 256 | 271.0 ms | 56.00 ms |
| 512 | 271.4 ms | 56.48 ms |
| 1024 | 287.2 ms | 54.78 ms |
| 2048 | 311.0 ms | 54.47 ms |
| 4096 | 314.1 ms | 54.29 ms |
| 6144 | 314.6 ms | 54.89 ms |

**怎么读：**

- TTFT 从 268.7 涨到 314.6（**+17.1%**），但注意涨幅集中在 512→2048 这一段，**2048 之后就平了**（311 / 314 / 315）。说明 TTFT 对块大小的敏感度有上限。
- TPOT 全程 54.27–56.48，**没有趋势**，与 graph 模式结论一致。
- 这组数据的绝对值不能引用（eager 慢 6.7 倍），只能看**相对差异**：块 128 → 6144，TTFT 差 17%，TPOT 差 0.8%。

### 6.3 两种模式为什么差 6.7 倍

| 指标（块 128，并发 1） | eager | CUDA graph | 倍率 |
|---|---:|---:|---:|
| TPOT | 54.47 ms | **8.15 ms** | graph 快 6.7× |
| TTFT | 268.7 ms | **219.0 ms** | graph 快 18.5% |
| 吞吐 | 0.14 req/s | **0.80 req/s** | 5.7× |

原因：CUDA graph 把"发射 30 层算子"这件事录制成一次调用，省掉了每个 token 几百次内核启动开销。解码每生成一个字都要走一遍，所以 TPOT 受益最大；prefill 只走一次，受益就小。

**这条差异不是块大小引起的，但它足以淹没块大小的效应**——所以绝对性能只能用 graph 模式的数据，eager 数据只能做相对比较。

### 6.4 长输入（16384 token，graph 模式）

| 块大小 | TTFT | TPOT |
|---:|---:|---:|
| 128 | 1,156.1 ms | 9.09 ms |
| 512 | 1,179.9 ms | 9.13 ms |

16K 输入下，块 128 → 512 的 TTFT 只涨 2.1%、TPOT 涨 0.4%，**比短输入下更不敏感**。（1024 档因显存不足没起来。）

## 七、第四组：并发吞吐看起来掉 73%，其实是容量问题

### 现象

固定 10 GiB、并发 32、160 个请求：

| 块大小 | 吞吐 |
|---:|---:|
| 128 | 2.15 req/s |
| 1024 | 1.57（−27%） |
| 4096 | 0.58（**−73%**） |

看起来"块越大吞吐越差"，而且差得离谱。

### 验证：换更大的 KV 预算再测一遍

同一批配置，只把 KV 预算从 10 GiB 提到 20 GiB：

| 块大小 | 10 GiB 预算 | 20 GiB 预算 |
|---:|---:|---:|
| 128 | 2.15 | 3.17 |
| 1024 | 1.57（−27%） | **3.13（−1.3%）** |
| 4096 | 0.58（−73%） | **2.23（−30%）** |

**结论：那 73% 的损失不是块大小的错，而是"池子太小装不下 160 个请求"。** 同样的块大小，只要给够显存，损失立刻从 −27% 缩到 −1.3%。

再用 graph 模式（util 0.95，容量 110k token）验证一次：128 / 256 / 512 的吞吐是 3.40 / 3.41 / 3.34，**只差 1.8%**。

三组数据互相印证：**容量充足时，块大小对并发吞吐几乎没有影响；看起来的损失全部来自"块大 → 容量小 → 请求排队"。**

## 八、第五组：注意力内核到底慢在哪

### 为什么还要看内核

端到端指标是"所有算子加起来"的结果。这个模型是 MoE，路由、专家矩阵乘、归一化、旋转位置编码都在抢时间，注意力可能只占一小部分。**要判断块大小有没有真的改变注意力计算，必须把它单独摘出来。**

### 怎么测

用 PyTorch 的 `torch.profiler` 录制服务进程的 CUDA 活动，从轨迹里过滤出注意力内核（`kernel_unified_attention`），分两个阶段各采一次：

| 阶段 | 负载 | 采到的样本数 |
|---|---|---|
| prefill | 8 条 × 4000 token prompt，只生成 1 个 token | 30 个（30 层 × 1 次前向） |
| decode | 8 条短 prompt，生成 96 个 token | 2,880 个（30 层 × 96 步） |

两个必须注意的坑：

1. **引擎必须与 profiler 同进程**，否则抓不到内核（vLLM v1 默认把引擎放在子进程，需要设 `VLLM_ENABLE_V1_MULTIPROCESSING=0`）；
2. **别把 `reshape_and_cache_kernel_flash` 算进来**——它负责"把新算出的 KV 写进页"，不是注意力计算。第一版没排除，导致 p50 被拉低一半。

### 什么是 CDF

CDF（累积分布函数）回答的是"**有多少比例的调用，耗时不超过 x**"。

```
累积比例
100% ┤                    ●──
 75% ┤              ●────
 50% ┤        ●────        ← 中位数 p50
 25% ┤   ●────
  0% └───┬────┬────┬───→ 单次内核耗时 (ms)
       0.8  3.0  6.0  15
```

比"平均值"强在两点：能看出**尾部**（最慢的那几次有多慢），也能看出**分布形状**（是集中在一点，还是分成两簇）。

### 结果

| 块大小 | prefill p50 | prefill p99 | decode p50 | decode p99 |
|---:|---:|---:|---:|---:|
| 128 | **0.846 ms** | **3.016 ms** | 0.0134 ms | 0.0171 ms |
| 256 | 1.838 | 6.076 | 0.0134 | 0.0171 |
| 512 | 3.833 | 10.988 | 0.0134 | 0.0171 |
| 1024 | 5.927 | 15.362 | 0.0134 | 0.0171 |
| 2048 | 5.925 | 15.314 | 0.0134 | 0.0171 |
| 4096 | 5.924 | 15.351 | 0.0134 | 0.0171 |

### 三条读法

**① prefill 内核从 0.846 涨到 5.927 ms，慢了 7 倍（+600%），而且 1024 之后完全饱和。**

这和端到端 TTFT 只有 +17% 并不矛盾：注意力只占 prefill 总时间的一小部分，其余是 MoE 和矩阵乘。**但内核对块大小极其敏感，这个事实在端到端指标里被稀释了。**

**② decode 内核六个档位一模一样，都是 13.4 µs（0% 变化）。**

这解释了端到端 TPOT 为什么完全不动：decode 阶段每步只处理 1 个新 token，页大小只影响一次页表查找，几乎无成本。而且数据只有 0.009 / 0.013 / 0.017 ms 三个离散值，已经接近计时分辨率。

**③ CDF 在 25/30 = 0.833 处有一个台阶，这是两类层造成的。**

30 层里 25 层滑窗、5 层全局。按这个比例分组：

| 块大小 | 滑窗层（25 个） | 全局层（5 个） | 倍数 |
|---:|---:|---:|---:|
| 128 | 0.846 ms | 3.009 ms | 3.56× |
| 512 | 3.832 ms | 10.970 ms | 2.86× |
| 4096 | 5.922 ms | 15.324 ms | 2.59× |

**所以表里的 p50 其实是"滑窗层"的耗时，p99 是"全局层"的耗时。** 全局层慢 2.6–3.6 倍，因为它的头维度是 512（滑窗层是 256），计算量更大。

### 为什么 prefill 会越变越慢

一个与数据吻合的解释（**待源码级确认**）：

滑窗层本来可以跳过窗口外的页——它只需要最近 1024 个 token。但**当页的粒度超过窗口大小后，这一页里既有窗口内的数据也有窗口外的数据，没法整页跳过**，只能按整页算：

- 块 128 → 8 页覆盖 1024 个 token，跳过其余页，计算量约 1024 token；
- 块 2048 → 页比窗口还大，每页都要整页算，计算量膨胀到接近整段长度；
- 块超过 1024 之后页无法再变粗，所以饱和。

## 九、把结论串起来

| 维度 | 128 → 4096 的变化 | 结论强度 |
|---|---|---|
| **TPOT（解码）** | **0%**（decode 内核恒定 13.4 µs） | 强，两种模式一致 |
| **TTFT（首字）** | +16.6%（graph 到 1024）/ +17.1%（eager 到 6144） | 强，2048 后饱和 |
| **并发吞吐** | 容量充足时 −2%；容量紧张时 −27%~−73% | 强，三组对照一致 |
| **可用容量** | −18%（47,326 → 38,836 token） | 强，固定字节下测得 |
| **prefill 注意力内核** | **+600%**（1024 后饱和） | 强，n=30×6 档 |
| **decode 注意力内核** | **0%** | 强 |
| 容量下限 | 块 <128 无额外收益 | 中（只有 16 和 64 两个点） |

### 三条实践建议

1. **别为了性能调大块大小。** 解码不受影响，首字反而更慢，容量还掉三分之一。
2. **块大小的主要成本在容量，而容量只在紧张时才咬人。** 如果你的服务显存富余（能装下所有并发请求的上下文），块大小基本可以随便选；如果显存吃紧，**小页带来的容量收益非常可观**。
3. **128 附近是最优区间。** 再小没有额外收益，再大开始亏容量和首字。

## 十、已知缺口与局限

| 项 | 说明 |
|---|---|
| 6144 的 prefill 内核数据 | 三次尝试都被拆成 2 批（样本数 60 而非 30），与 chunked prefill 的批预算（8192 token）+ 块 6144 页粒度有关，暂不能与其余档比较 |
| 块 32 的 graph 模式 | 多轮启动失败，未定位；eager 模式并发 1 能跑（245.7 ms / 54.11 ms） |
| 16 / 64 的 eager 模式 | 服务一接请求引擎就退出（同参数换 graph 模式正常），属小页在 eager 路径上的不稳定 |
| 2048 / 4096 / 6144 的 graph 模式 | 单卡放不下（图录制需 40 / 80 / 120 GiB），需 TP=4 |
| 每格只有一次测量 | 没有重复实验与置信区间，是本批数据最大的局限；判断差异时应把 2–3% 以内视为噪声 |
| 只测单卡 | 未验证 TP=2/4 下的行为 |
