# Qwen3.8 KV 预算与吞吐实测

> 实验状态：并发 16（4 臂）、并发 20（4 臂）已完成；并发 24 完成 1.0B0 单臂探索后停止；并发 18（4 臂）排队等待空闲卡。
> 运行环境：4 × NVIDIA A800-SXM4-80GB（TP4 + EP，每臂启动前执行独占校验），vLLM（commit `4ba787ec` + exact-stop 结算补丁），`Qwen3.8-Flash-Next-FP8`（172.78 GiB），AgentX 1.0.7（固定 Weka 256K trace，seed 42，APC 开启）。
> 统计口径：全部 9 个正式臂均满足 `normalization.exact = true` 且 `reconciliation.status = matched`，无估算值或补零项。
> 相关实验记录：[混合注意力 block size 实测](/notes/ai-infra/block-size-weekly)、[SWA/Full 模型 block size 实测](/notes/ai-infra/block-size-gemma4)。

## 一、实验背景与问题

在混合注意力模型的显存管理研究中，vLLM 当前采用分组打包和统一页大小的方式管理多种异构缓存对象（Full Attention KV、线性/循环状态、SWA 等），这带来了两类问题：一是全注意力 `block_size` 受统一页约束而不可自由调节（前两篇记录已量化其对容量与 prefill 算子的影响），二是各组之间存在明显的结构性页内显存浪费。

组内前期在相同环境（`Qwen3.8-Flash-Next-FP8`，vLLM TP4，AgentX Weka 256K）下的埋点实测显示，常驻缓存的结构性浪费峰值达到 14.1% 至 19.0%（并发 16 下活跃 KV 浪费峰值达 22.0%）；在缓存对象更复杂的 DeepSeek V4 Flash 上，结构性浪费进一步升至 20% 至 37%。后续显存管理方案计划通过虚拟内存 API（VMM）为各类缓存对象独立映射物理页、回收这部分结构性浪费。在进入系统实现前，需要先定量验证「显存收益到吞吐收益的换算关系」：如果把回收的 10% 至 30% 显存重新投入 KV 缓存池，端到端服务吞吐与延迟能获得多大幅度的改善。

本实验不实现具体的碎片回收机制，直接沿用上述模型、并行配置与 Weka 256K 负载，通过在 vLLM 初始化阶段显式设置 `--kv-cache-memory-bytes` 调节每卡 KV 预算（`1.0B0`、`1.1B0`、`1.2B0`、`1.3B0`），在精度与计算配置保持不变的前提下回答两个问题：

1. 在 AgentX 长上下文多轮代理负载下，将每卡 KV 预算增加 10% / 20% / 30%，可见输出吞吐和端到端延迟分别变化多少。
2. KV 预算扩容的收益如何随并发度变化，系统在什么工作区间真正受到 KV 容量约束。

承接组内前期在并发 8 / 16 / 24 下的负载观测（并发 16 吞吐较高，并发 24 因显存紧张性能明显下降），第一轮实验先在并发 16 下完成了四档预算测试。结果虽然单调上升（从 236.126 tok/s 增至 270.952 tok/s，最高增幅 +14.75%），但边际收益衰减很快，预算转换比（吞吐相对增益除以预算相对增幅）在 +20% 和 +30% 档位分别降至 0.698 和 0.492。单看这组数据，容易得出“增加 KV 预算性价比偏低”的印象。

核查同批运行的服务端引擎监控后发现，并发 16 下 GPU KV cache 利用率均值仅 21.9% 至 31.8%，P95 利用率在 `1.0B0` 基准档也只有 58.1%（`1.3B0` 降至 42.2%），等待队列均值仅 0.11 至 0.26 个请求。在并发 16 时，KV 缓存池处于充裕状态，制约吞吐上限的因素是并发请求数不足，新增预算大部分处于闲置状态。

为验证 KV 进入容量受限区间后的实际弹性，第二轮实验保持模型、trace、1800 秒计量窗口和四档预算不变，仅提高 AgentX 并发度至 20 并重跑全部四臂；随后在并发 24 下执行 `1.0B0` 单臂探索，复现并剖析前期观察到的显存紧张退化现象。并发 24 在基准预算下即出现严重过载，因此停止其后续三臂，改为规划补测并发 18，以进一步确定 16 到 20 之间的拐点位置。

## 二、实验配置与统计口径

### 2.1 模型、引擎与硬件环境

| 配置项 | 参数与说明 |
|---|---|
| 服务器与 GPU | A800-1 / NSL-A800-1，4 × NVIDIA A800-SXM4-80GB |
| 基础镜像 | `nvcr.io/nvidia/pytorch:25.02-py3`，依赖 torch `2.14.0+cu126`、vLLM `0.33.0+precompiled`、transformers `5.20.2` |
| 模型权重 | `Qwen3.8-Flash-Next-FP8`（`Qwen4ExpForConditionalGeneration`，131 分片，185,523,317,458 B，约 172.78 GiB） |
| 服务代码 | vLLM commit `4ba787ec9959e566d3b587a796dff07673324da5`（含 12 文件源码快照 diff 与 exact-stop 结算补丁） |
| 并行与解码 | TP4 + EP（4 卡）；MTP 投机解码（`num_speculative_tokens = 3`） |
| KV cache 配置 | FP8 KV + BF16 indexer KV；APC（Automatic Prefix Caching）开启；`--prefix-cache-retention-interval 0` |
| 调度与显存 | `--max-num-seqs 256`，基线校准使用 `--gpu-memory-utilization 0.85`，正式臂由 `--kv-cache-memory-bytes` 显式覆盖 |
| 加载与系统配置 | 权重加载策略 `eager`；`PYTORCH_ALLOC_CONF=pinned_max_round_threshold_mb:1024`；CPU 亲和性绑定 NUMA 节点 1（核 26–51） |
| 解析器配置 | `--enable-auto-tool-choice`，`--tool-call-parser qwen3_coder`，`--reasoning-parser qwen3` |

服务进程在每个预算臂启动前均完全重启，不使用 flush cache 替代重启，避免不同档位之间的缓存状态残留。

### 2.2 负载数据与预算档位

客户端压测沿用 `agentx-harness==1.0.7` 的 `agentx profile` 场景，不升级至新版默认配置，以保持与前期历史基线的口径一致：

- **输入数据集**：本地 Weka 256K trace（`weka_trace`），共 393 条会话轨迹、28,444 轮主代理交互、1,697 个子代理组、39,822 个子代理内部请求，合计 68,266 条模型请求、6,891,228,864 input tokens 与 58,728,807 output tokens。全部请求的 `input + output` 最大值为 255,999，无超过 256,000 的样本。全部 393 个文件已做逐文件 SHA-256 锁定（清单汇总哈希 `84f7a0ad0c0c8087c591b6d11548c415e19ae7944254f28e1ecbfcc9648017ec`）。
- **压测参数**：`random_seed = 42`，warmup 为每条 lane 10 个请求，trajectory 起点范围 0.25–0.75，开启 streaming，token 计数采用服务端返回值。需要说明的是，AgentX 的 concurrency 指同时存活的 session tree（lane）数量，子代理扇出会产生高于该数值的瞬时并发请求，不能与 vLLM 的 `max-num-seqs` 等同。
- **预算校准与四档定义**：先在 `--gpu-memory-utilization 0.85` 下测得每卡初始化 KV 预算基线 `B0 = 27,721,816,167` bytes（约 25.82 GiB）。基线对应的实际共享 backing 显存为 27,711,590,400 bytes/卡，共分配 2,313 个物理块（2,312 块可用），单块大小 11,980,800 bytes。正式实验按整数字节取整设定四档预算：

| 预算档位 | 每 GPU 初始化 KV 预算（bytes） | 约合容量（GiB/GPU） | 相对 B0 比例 | 预算增幅 $m_i$ |
|---|---:|---:|---:|---:|
| `1.0B0`（b100） | 27,721,816,167 | 25.82 | 1.00× | 0.0% |
| `1.1B0`（b110） | 30,493,997,783 | 28.40 | 1.10× | +10.0% |
| `1.2B0`（b120） | 33,266,179,400 | 30.98 | 1.20× | +20.0% |
| `1.3B0`（b130） | 36,038,361,017 | 33.56 | 1.30× | +30.0% |

### 2.3 计量窗口、对账要求与指标定义

- **计量窗口**：正式 issuance 窗口为 1800 秒（30 分钟），grace 窗口为 1800 秒，使发送窗口关闭前已发出的请求能够自然收尾。主吞吐指标的分母严格采用实际 profiling 窗口 `sent_end_ns - start_ns`（实测 9 个臂均在 1800.000 至 1800.001 秒之间），仅统计完整落在该窗口内且成功完成的请求的**可见输出 token**（不包含 reasoning token 与 drain 阶段产出）。同时在辅助口径中单独记录包含 reasoning 在内的全量输出吞吐（`reasoning_plus_output_tokens_s`）。
- **精确对账规则**：启用 exact-stop 结算补丁与全阶段 export/ACK 对账，强制要求每臂同时满足 `normalization.exact = true`、`reconciliation.status = matched` 且请求错误数为 0。若出现 warmup 异常、drain 强制取消或对账不一致，直接拒收该臂并重跑。
- **GPU 独占校验**：每臂启动前检查所选 4 张 A800 显存占用均 `<= 64 MiB` 且无其他计算进程，确保 1800 秒计量窗口内不受集群其他任务干扰。
- **衍生指标定义**：设基准预算 `1.0B0` 下的可见输出吞吐为 $T_0$，第 $i$ 档预算 $B_i$ 下的可见输出吞吐为 $T_i$，则预算相对增幅 $m_i = B_i / B_0 - 1$，吞吐相对增益 $g_i = T_i / T_0 - 1$，预算转换比 $r_i = g_i / m_i$。当 $r_i > 1$ 时，表示每增加 1% 的 KV 预算换来超过 1% 的吞吐增长（超线性收益）；$r_i < 1$ 则处于亚线性区间。

## 四、1800 秒窗口动态与机制分析

为了解释不同并发与预算组合下吞吐差异的物理成因，下面直接从 vLLM 服务端导出指标（`agentx/server_metrics_export.csv`）和 10 秒级引擎运行日志（`server.log.gz`）提取全窗口内部状态。需要说明的是，此前初步整理中曾引用客户端 `client.log` 的粗粒度采样（每臂约 57–63 个点，给出 `c16/c20/c24` 基准 KV 峰值为 59.9% / 81.2% / 95.5%）；本文以下表格与图表统一采用精度更高的 vLLM 引擎原生监控数据（10 秒级，每臂约 180 个采样点），两者趋势完全一致，引擎侧能更准确地捕捉瞬时峰值与前缀缓存命中率。

### 4.1 引擎时序监控

图 2 将四个代表臂（`c16-b100`、`c20-b100`、`c20-b130`、`c24-b100`）的 10 秒级引擎日志按 `normalization.json` 的窗口起点对齐到 0–30 分钟，同步呈现 KV 利用率、等待队列深度和累积 Prefix Cache 命中率的演化过程。

![1800 秒压测窗口内部动态时序](/img/qwen38/qwen38_timeseries_dynamics.png)

结合三个子图可以清晰看到窗口内的动态演变：

1. **前 5 分钟的起量与分叉**：0 至 5 分钟处于轨迹起步阶段，四条曲线的 KV 利用率都在 30% 以下，等待队列为 0，前缀缓存命中率均在 80%–85% 之间。第 5 分钟后长上下文会话集中涌入，四个工况迅速分化。
2. **`c24-b100` 的持续饱和与缓存失效率上升**：第 6 分钟起，`c24-b100` 的 KV 利用率直接冲过 80% 并在后续 24 分钟内多次触及 95%–100% 上限（P95 达 94.7%）；等待队列长期维持在 5 至 18 个请求之间（均值 5.65，P95 为 12）；图 2(c) 中其累积 Prefix Cache 命中率从第 5 分钟的约 84% 呈近似直线下滑，至窗口结束跌至 54.8%。
3. **`c20-b100` 与 `c20-b130` 的对照**：`c20-b100` 在窗口后半段（15–30 分钟）频繁逼近 80% 警戒线（P95 为 76.5%，峰值 84.7%），伴随间歇性排队尖峰（最高 12 个请求），Prefix Cache 命中率回落至 81.9%。将每卡预算增加 30% 至 `c20-b130` 后，KV 利用率曲线整体下移至 30%–55% 区间（P95 降至 54.8%，峰值 66.0%），等待队列均值从 0.93 降至 0.34，Prefix Cache 命中率抬升至 89.7%（+7.8 个百分点），与轻压的 `c16-b100`（89.5%）基本重合。

1. **前缀缓存驱逐与大规模 Prefill 重算**：在多轮 AgentX 长上下文会话中，历史上下文高度复用。当活跃请求的 KV 占用逼近物理池上限时，APC 缓存池中可保留的历史 prefix blocks 被迅速驱逐，命中率从约 90% 跌至 `c20-b100` 的 81.9% 乃至 `c24-b100` 的 54.8%。大量原本可直接命中的超长前缀被迫重新执行 prefill，消耗了主要算力。
2. **准入排队积压与 Prefill/Decode 干扰**：KV 池接近满载后，调度器将新到达请求挡在 waiting 队列中（`c24-b100` 平均等待 5.65 个请求，峰值 18 个），同时频繁的长序列重算 prefill 严重拖慢了正在运行请求的解码步长。

2. **并发 20 下扩容大幅改善解码流畅度（ITL）**：并发 16 的 ITL P95 全程稳定在 40.0 至 45.3 ms。并发 20 在 `1.0B0` 基准下，受高频重算 prefill 干扰，ITL P95 被拉高至 97.4 ms；扩容至 `1.3B0` 后降至 47.7 ms（降幅 51.0%），基本回落到并发 16 的水平。同时 E2E P95 从 118.2 秒降至 74.9 秒（降幅 36.6%）。
3. **并发 24 过载时的延迟构成**：在 `c24-b100` 上，不仅尾部延迟恶化，中位数也全面失守（TTFT P50 达 25.60 秒，ITL P50 达 185.7 ms，E2E P50 达 62.7 秒）。图 4(c) 对比了服务端排队 P95 与端到端 TTFT P95：在 `c24-b100` 下，vLLM 排队延迟 P95 高达 43.34 秒，约占 TTFT P95（62.44 秒）的 69%；而在 `c20-b100` 下排队 P95 为 10.31 秒，扩容至 `c20-b130` 后降至 4.80 秒（与 `c16-b130` 的 4.74 秒持平）。

## 六、容量规划与配置参考

在长上下文多轮代理负载下，评估“增加 KV cache 预算是否划算”必须与目标并发度和引擎实时利用率绑定。结合上述 9 臂实测，可以按服务端 KV P95 利用率、等待队列和前缀缓存命中率划分为三个操作区间：

| KV P95 利用率区间 | 实测对应工况 | 系统瓶颈特征 | 配置与调优建议 |
|---|---|---|---|
| **< 60%** | 并发 16 全程（42.2%–58.1%）、`c20-b130`（54.8%） | KV 池充裕，Prefix 命中率约 90%，吞吐受并发度限制 | 增加 KV 预算对吞吐的转换比低于 1（主要改善 TTFT 尾延迟），优先考虑适度提高并发 |
| **60% – 80%** | `c20-b100` 至 `c20-b120`（61.3%–76.5%） | KV 容量成为直接约束，Prefix 命中率滑落至 82%–88%，ITL 与排队抬头 | 增加 KV 预算收益最高的区间，吞吐转换比可达 1.40× 至 2.59×，同时显著压低 TTFT/ITL P95 |
| **≥ 80%（峰值逼近 100%）** | `c24-b100`（P95 94.7%，峰值 100%） | Prefix 缓存剧烈驱逐（命中率 54.8%）、排队积压与重算干扰导致过载退化 | 吞吐较并发 20 下降约 5 倍、排队 P95 超过 43 秒，必须先扩充 KV 预算或对并发限流 |

如果业务侧更关注交互尾延迟（例如要求 TTFT P95 控制在 5 秒以内），即便 KV P95 已低于 60%，适度预留 10%–20% 的 KV 缓冲空间仍然对压低偶发长前缀重算有直接帮助。

## 七、实验说明与后续计划

### 7.1 环境说明与适用边界

- **权重加载与启动期**：模型权重位于共享存储盘，加载阶段曾受集群其他任务 I/O 影响耗时较长，启动期做了页缓存预热与空闲等待；这些操作仅发生在服务启动阶段，不影响 1800 秒正式计量窗口的统计结果。
- **运行时状态**：服务端使用带补丁的 vLLM 运行时（启动参数含 `--allow-uncertified-runtime`），官方 runtime certification 尚未完成。
- **外推边界**：本实验通过初始化参数直接增大 KV 显存预算，用于衡量固定并发下的容量敏感性，不能直接等同于某项具体碎片回收算法的端到端加速比（后者还需扣除回收机制自身的运行时开销与布局变更影响）。此外，全部实验均在 APC 开启条件下测得，未剥离普通容量扩容与前缀缓存复用的各自贡献。

## 八、小结与复现信息

本轮跨并发 KV 预算实验表明，KV cache 容量对长上下文推理吞吐的边际收益高度依赖并发负载所处的工作区间。在并发 16 下，KV P95 利用率始终低于 60%，前缀缓存命中率维持在 89.5%–91.8%，新增预算主要改善了 TTFT 尾延迟（P95 下降 58.1%），对吞吐的转换比在 +20% 以后低于 1。将并发抬升至 20 后，基准档 KV P95 达到 76.5%、前缀命中率降至 81.9%，此时增加 10% / 20% / 30% KV 预算带来 +25.88% / +38.02% / +41.91% 的可见输出吞吐增益（转换比 2.588 / 1.901 / 1.397），同时完成请求数提升 33.3%、ITL P95 下降 51.0%。并发继续增至 24 后，基准预算下 KV 触及 100% 满载，前缀命中率滑落至 54.8%，排队 P95 达 43.34 秒，可见输出吞吐跌至 38.224 tok/s。
