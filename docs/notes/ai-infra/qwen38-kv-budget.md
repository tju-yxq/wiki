## 二、为什么要做：从并发 16 的"伪结论"说起

长上下文推理中，KV cache 是显存里最大的可变开销。每张卡给 KV 分多少字节（`kv_cache_memory_bytes`）直接决定系统能同时驻留多少条长会话、是否因容量不足触发抢占与重算（recompute），以及最终吞吐上限。

我们要回答的直接工程问题是：**在 AgentX 长上下文负载下，把每卡 KV 预算按 `1.0B0 → 1.1B0 → 1.2B0 → 1.3B0` 递增，吞吐能涨多少？这份显存代价划不划算？**

第一轮在**并发 16** 跑完四臂后，吞吐从 236.126 涨到 270.952 tok/s（+14.75%），每 +10% 预算的边际收益迅速衰减，转换比（吞吐增益 ÷ 预算增幅）从 1.186 掉到 0.698 再到 0.492。如果只看这组数字，会得出"KV 预算性价比低"的判断。

但同批运行的客户端采样揭穿了这个判断：
- 并发 16 时，**KV 利用率峰值只有 59.9%**（1.3B0 时仅 45.2%）；
- 等待 prefill 的队列读数均值仅 **8.3** 个。

**KV 从头到尾都没被压满。** 限制吞吐的不是 KV 容量，而是并发不够、系统没能力把多给的预算用起来。因此第二轮固定模型、trace、1800 s 计量窗口与预算序列，**只抬高并发**（20 → 24，并规划补测 18），验证 KV 进入饱和区后的真实预算弹性。

### 计量口径与证据契约

- **计量窗口**：issuance 1800 s + grace 1800 s。主指标为 **issuance 窗口内成功完成的可见输出 token 速率（tokens/s）**；reasoning 与 drain 阶段产出不计入。
- **零妥协对账**：exact-stop 结算 + all-phase export/ACK 对账，强制要求 `normalization.exact = true` 且 `reconciliation.status = matched`。任何请求错误或对账不符直接判该臂失败并重跑，不放松契约、不取估算值。
- **GPU 独占校验**：每臂启动前校验四张卡 `memory.used ≤ 64 MiB` 且无其他计算进程，避免共租污染计量窗口。
- **卡组与横向可比性**：集群共用，并发 16、并发 20（及 1.3B0 换卡）和并发 24 使用的 4 卡槽位不完全相同（详见第七节）。**跨并发组的绝对吞吐不可直接硬比，核心可比量是组内增益斜率（转换比）与 KV 利用率**。

## 五、机制解释：KV 利用率与排队深度

从各臂 `client.log` 提取全窗口 `kv_usage` 与 `queue` 采样（每臂约 57–63 个采样点），可以把**"预算 → 利用率 → 排队/抢占 → 吞吐"**的因果链完全量化出来：

| 臂 | KV 均值 | KV 峰值 | 队列运行读数均值 | 队列峰值（running / waiting） | 吞吐 (tok/s) |
|---|---:|---:|---:|---|---:|
| `c16 · 1.0B0` | 31.0% | 59.9% | 8.3 | 22r / 6w | 236.126 |
| `c16 · 1.1B0` | 28.3% | 57.6% | 7.9 | 21r / 5w | 264.133 |
| `c16 · 1.2B0` | 25.1% | 50.5% | 7.8 | 20r / 3w | 269.094 |
| `c16 · 1.3B0` | 21.5% | 45.2% | 7.1 | 19r / 1w | 270.952 |
| `c20 · 1.0B0` | 49.5% | **81.2%** | 13.4 | 23r / 9w | 190.313 |
| `c20 · 1.1B0` | 42.1% | 70.2% | 12.3 | 20r / 6w | 239.569 |
| `c20 · 1.2B0` | 35.9% | 65.3% | 11.5 | 24r / 4w | 262.670 |
| `c20 · 1.3B0` | 33.4% | 57.9% | 11.5 | 23r / 10w | 270.073 |
| `c24 · 1.0B0` | **67.3%** | **95.5%** | **21.6** | **31r / 17w** | **38.22** |

三条直接规律：
1. **并发推高 KV 压力**：同样 `1.0B0` 预算，并发 16 → 20 → 24 时，KV 峰值从 `59.9% → 81.2% → 95.5%`，均值从 `31.0% → 49.5% → 67.3%`，队列深度同步翻倍。
2. **加预算直接卸压**：并发 20 下每加 10% 预算，KV 峰值从 `81.2% → 70.2% → 65.3% → 57.9%`，卸掉抢占与排队压力后，吞吐迅速回升至 270 tok/s，基本追平并发 16 的平台值（且完成了更多请求：1,281 vs 934）。
3. **饱和阈值决定边际收益**：当 KV 峰值已经落到 60% 以下（如 `c16` 全程、`c20 · 1.3B0`），继续加预算不再解除瓶颈，曲线进入平台期。

## 六、工程含义与预算配置建议

给长上下文服务配 KV 预算时，**脱离并发谈"加预算值不值得"没有意义**。应先在目标并发下观测 KV 峰值，再分三段决策：

| KV 峰值区间 | 对应实测工况 | 瓶颈判断 | 工程建议 |
|---|---|---|---|
| **< 70%** | 并发 16 全程（45%–60%） | 并发不足，KV 未饱和 | 加预算性价比低（转换比 < 1），应优先提并发 |
| **80% – 90%** | 并发 20 · `1.0B0`（81.2%） | **KV 容量成为直接约束** | **加预算收益最高区间**，转换比可达 1.4–2.6（超线性） |
| **> 95% + 队列积压** | 并发 24 · `1.0B0`（95.5%，队列 27r） | 过饱和、持续抢占重算 | 吞吐断崖式崩塌，必须先扩 KV 预算或限流降并发 |

## 七、局限、披露与待补工作

### 必须披露的实验限制

- **单次运行（n = 1）**：每臂仅跑一次，所有比较均为点估计，不声明置信区间或重复性。
- **卡组差异**：因集群共用，四组 GPU UUID 不完全一致，尤其是 `c20 · 1.3B0` 原卡组被他人长期占用，改用了空闲四卡（跨臂硬件槽位不同可能带来小幅绝对偏差，但不影响单臂精确对账）：
  - 并发 16：`48bfce1e, 1b785b31, 7ca0db16, 2d781693`
  - 并发 20（`1.0 / 1.1 / 1.2B0`）：`48bfce1e, 2d781693, 6238fbba, ba9b950c`
  - 并发 20（`1.3B0`）& 并发 24（`1.0B0`）：`1b785b31, 95787a56, 2649b690, ba9b950c`
- **集群共租与加载期干预**：模型共享盘在加载阶段受他人 I/O 拖慢数小时；`prewarm`（页缓存预热）、`idle_wait`、`launch_retries` 均完整记录在 campaign JSON 中，仅影响启动耗时，不改变 1800 s 计量窗口语义。
- **运行时认证**：使用 documented patched runtime（`--allow-uncertified-runtime`），runtime certification 尚未完成。
- **失败重试留痕**：`c20 · 1.3B0` 曾失败 2 次（一次 warmup 空输出触发契约拒收、一次启动窗口 GPU 被抢占），失败臂目录与 `run.json` 均保留在交付包内可供审计。

## 八、结论与复现信息

### 四条核心结论

1. **并发 16 的"加预算不划算"是未饱和区造成的伪结论**：KV 峰值不到 60%，预算没被用起来，转换比 < 1。
2. **并发 20 才是 KV 预算真正兑现价值的区间**：B0 峰值 81.2%，+10%/+20%/+30% 预算换来 +25.88%/+38.02%/+41.91% 吞吐，转换比 2.588 / 1.901 / 1.397（全程超线性）。
3. **并发 24 已越过容量悬崖**：B0 下 KV 95.5%、队列积压 27r，吞吐塌至 38.22 tok/s（降约 5 倍），说明存在明确的最优并发窗口，而非并发越高越好。
4. **工程决策应以 KV 峰值为锚**：峰值 < 70% 先提并发，80–90% 加 KV 预算最划算，> 95% 必须先扩容或限流。
